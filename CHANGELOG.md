# Changelog

## Unreleased

- On a Node older than 24, every command stops before it reads its arguments or starts a run, and prints the error envelope `{"error":"firstlight needs Node 24 or newer (found v20.19.0)","do":"install Node 24 or newer, then rerun the same command"}` with exit code 1. Before, an older Node could run firstlight on a version it was never tested on.

## 0.2.0 (2026-10-13)

`0.1.0` was removed from npm on 2026-10-12, and npm does not let a removed version be published again. `0.2.0` holds everything in `0.1.0` and the changes below.

- `firstlight run --failed` runs only the checks of the latest run that did not pass (`failed`, `timed_out`, `skipped`, `cancelled`, or `unknown`). Each one resolves against the current `firstlight.json` like a name given to `run`: a configured check comes with its `after` checks, and reused passes still apply. A script or shell command from the command line runs the same command again, and a configured check removed from `firstlight.json` is left out. With no run yet, or no check that did not pass, it prints the error envelope with `firstlight run` and exits 1. It takes no check names.
- `firstlight follow` attaches to the latest run and prints one line for each status change, from the first one, as it happens: `test passed (exit 0, 10.4s)`, or `typecheck failed (exit 2, 3.5s)` with the same log tail that `run` prints. It ends with the summary lines of `results --wait` and exits with the same code. `--json` prints one check object per change, in the shape of `results --json`, then the summary. Each line is written on its own, so a line watcher such as Claude Code's Monitor sees it at once. `follow` never writes `events.jsonl`.
- A failed or timed-out check prints its diagnostics before the log tail, as `file:line:col rule message` lines, when firstlight can read the tool's output. The parsers read the text of `tsc` (plain and `--pretty`), the vitest default reporter, `node --test` (spec and TAP reporters), and `archstrict check`. A test's diagnostic names the test's full name and the first stack frame inside the repository. With diagnostics, the log tail is 10 lines instead of 40. A check shows at most 20 diagnostics, then a count of the rest. In `--json`, each diagnostic is a `{"type":"diagnostic","check","file","line","col","rule","message"}` line after its check, and the check has `more_diagnostics` when some were left out. Without a parser, or with no diagnostics, the output does not change. This applies to `run`, `results`, and the failure lines of `follow`.
- `firstlight results --new` reports only the failures that the previous run did not have, and counts the rest: `not new: 2 failures already in the previous run, 3 passed`. The previous run of a check is the newest earlier kept run in which the same check, with the same `run` command, passed, failed, or timed out. A diagnostic is new when that run has none of the same check with the same file, rule, and message; the line and column do not count, so moved code is not new. A failure without diagnostics is new when the check did not fail in that run. Without a previous run, every failure is new, and one line says so. It exits 1 only for a new failure, or for a check that is still running, was cancelled, or is unknown. It works with `--wait`. With `--json`, each check gains `new` and `baseline` (and `old_diagnostics` when it failed), only new diagnostics are printed, and the summary gains `new`, `new_failures`, `old_failures`, and `no_baseline`.
- A vitest diagnostic shows the evidence file and the rerun command that depug's reporter printed for its test, as `evidence: <path>` and `rerun: <command>` lines under the diagnostic. In `--json`, the diagnostic line gets `evidence` and `rerun` fields. firstlight matches by the test file and the full test name in depug's rerun command; when two failed tests or two depug failures have the same file and name, or depug printed nothing for a test, it attaches nothing. A log without depug lines gives the same diagnostics as before. This applies to `run`, `results`, `results --new`, and `follow`.
- A check in `firstlight.json` takes `parser`: `tsc`, `vitest`, `node-test`, `archstrict`, or `none`. Any other value is a config error. Without it, firstlight infers the parser from a simple `run` command (`tsc`, `vitest`, `node --test`, `archstrict`), and from the script that `npm run <script>` or `npm test` runs, one level deep.

## 0.1.0 (2026-10-12)

The first version of firstlight.

- `firstlight run` starts every check from `firstlight.json` in parallel and returns at the first check that fails or times out. It prints that check's exit code, the last 40 lines of its log, the status of the other checks, and the next command. The other checks keep running. When every check passes, it prints one line and exits 0.
- `firstlight run <check>...` runs only the named checks and the checks they are `after`.
- `firstlight run` reads like npm-run-all's `run-p`: `firstlight run lint typecheck test` runs those `package.json` scripts in parallel as `npm run <script>`, and `firstlight run "lint:*"` runs every script that matches the pattern, in `package.json` order. `*` matches inside one `:`-separated segment, and `**` matches across segments. A check of the same name in `firstlight.json` comes first, with its `after` checks. An unknown name, or a pattern that matches no script, prints the error envelope with the configured checks and the scripts.
- A check can be any shell command, given on the command line: an argument with whitespace, like `firstlight run "bundle exec rubocop" "bundle exec rspec"`, or any argument after `--`, like `firstlight run lint -- make`. Its name is the command itself. The checked project needs no `package.json`.
- A log file name replaces each character outside `[A-Za-z0-9._-]` in the check name with `_`, and adds `-2`, `-3`, and so on when two checks of a run would share one file. The check name in the output stays as written.
- A second `firstlight run` stops the checks still running from the previous run before it starts.
- `firstlight results` reports the latest run, and `--wait` blocks until every check is done. It exits 1 when any check failed, timed out, was skipped or cancelled, or is unknown. `firstlight stop` cancels the running checks, and does nothing when none are running.
- A check can wait for other checks with `after`. If one of them does not pass, the check is `skipped`. A check that runs longer than `timeoutSec` (600 by default) is stopped and recorded as `timed_out`.
- Without `firstlight.json`, the `package.json` scripts `lint`, `typecheck`, `test`, and `archstrict` become checks.
- A detached supervisor per run starts the checks, each in its own process group, and records every status change in `events.jsonl` under `$XDG_STATE_HOME/firstlight/`. Nothing is written into the checked repository. The newest 20 runs are kept.
- If the supervisor dies before a check finishes, that check is reported as `unknown` with `orphan: true`, and no exit code is invented.
- A running or pending check shows about how long it has left, and the `next: firstlight results --wait` line shows the time left for the whole run. The estimate comes from the newest pass of the same check, with the same `run` command, in the kept runs. A running check past that duration says `past its usual` instead. Without that history, no estimate is shown. In `--json`, each check has `eta_ms` and `overdue`, and the summary has `eta_ms`.
- `firstlight run` reuses a pass instead of running the check again when a kept run passed it on the same working tree with the same command, and its `after` checks did the same. The working tree is a git tree hash of the tracked and untracked files, without ignored files, computed through a temporary index, so the real index and refs do not change. The text says `test passed (cached from run 01K..., 10.4s originally)`, the all-passed line counts the reused checks, and in `--json` each check has `cached_from`. Only a pass is reused. Environment variables and files outside the repository are not part of the comparison; `firstlight run --no-cache` runs every check anyway and still records its keys. Outside a git repository nothing is reused.
- `--json` prints JSON Lines: one object per check and one summary. A failure of firstlight itself prints `{"error","do"}` on stderr and exits 1.

Development:

- Runtime code still uses Node built-ins only. Development now uses TypeScript for `npm run typecheck`, vitest for `npm test`, Hegel property tests for the state machine, `after` validation, and run ids, archstrict for module boundaries and the layer order (`npm run archstrict`), Stryker with stryker-agent-reporter for mutation testing (`npm run mutation`), and depug, which prints an evidence file and a rerun command for each failed test. Every version is pinned exactly.
- The tests moved from `node:test` to vitest and assert the same behavior.
- `firstlight.json` makes firstlight check itself: `typecheck`, `test`, `archstrict`, and a scoped `mutation` run, in parallel.
- CI runs `npm ci`, `npm test`, `npm run typecheck`, and `npm run archstrict` on Node 24, with the actions pinned to commits.
- The package is ready to publish to npm as `firstlight`: `npm i -D firstlight` installs a `firstlight` bin. `npm run build` compiles `src/` to `dist/` with tsc, rewriting the `.ts` relative imports to `.js`, because Node does not strip types from files under `node_modules`. `prepack` runs the build, and the tarball holds `dist/`, `README.md`, `CHANGELOG.md`, `LICENSE`, and `package.json`. The supervisor starts from the same compiled file as the CLI.
- `test/pack.test.ts` packs the package, installs the tarball into a temporary project, and runs the installed bin: `--help`, and a `firstlight run` of a passing shell command.
- `.github/workflows/publish.yml` publishes a `v*` tag to npm through a trusted publisher after the GitHub Environment `publish` approves it, with provenance, then creates the GitHub release from that version's changelog section. `docs/releasing.md` lists the one-time bootstrap and the steps for each version. `SECURITY.md` points to private vulnerability reporting.
